# Checkpoint version compatibility

Read the installed task-checkpoint skill and runtime version before diagnosing a stop. Old saved instructions describe their original runtime; they cannot override the current user or restore removed behavior.

| Contract | Quota boundary | Continuation |
| --- | --- | --- |
| task-checkpoint 0.7 | Persistent automatic quota stop and preservation state | Its supported reviewed-resume procedure |
| task-checkpoint 0.8 | Save a verified handoff at the chosen remaining-usage limit, then end that run; no tool-blocking hook or persistent pause | Current explicit continuation after recovery, or a direct percentage/exhaustion choice, without a grant/review ceremony |

An explicit human stop, native permission denial, active foreign owner or uncertain external operation remains independent of quota policy. A current user may authorize a bounded read-only verification while implementation stays stopped. Verify that scope from the actual human request; if trusted cross-chat evidence is available, use it instead of requesting the same approval again. A later distinct implementation instruction must be handled as its own authority and phase.

For stale telemetry, inspect the effective selected observation and the existing collector separately. Missing, stale, future and past-reset readings are unknown. Preserve account/window identity and explicit source selection; never replace a scoped observation with another account or manufacture healthy readings. The 0.8.1 collector-selection repair uses a fresh same-account collector when project quota readings are entirely unknown or absent, while retaining current project readings and non-quota limits.

Separate source tests, installed bytes and actual native execution. Verify ordinary tools in the affected chat when authorized; a read-only project inspection alone does not prove that native check ran. Leave legitimate holds and other writers untouched. Do not restart a trial or implementation to make a verification pass.
